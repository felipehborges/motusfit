# 0002 — API: Hono + oRPC (contract-first) em Node 24

- Status: aceito
- Data: 2026-07-18

## Contexto

A API serve dois clientes TS próprios (web, mobile) e futuramente pode expor API pública (wearables, parceiros). Requisitos: type safety ponta a ponta, API versionada, documentação automática, estrutura sustentável por anos.

## Decisão

- **Framework HTTP: Hono 4** rodando em **Node 24 LTS**.
- **Camada de API: oRPC 1.x contract-first** — contratos em `packages/contracts` (Zod 4), montados no Hono sob `/api/v1`, com **OpenAPI 3.1 gerado do contrato** e docs Scalar em `/api/v1/docs`.
- Estrutura interna própria (handler → use case → repository), já que Hono não impõe arquitetura — documentada em [architecture.md](../architecture.md).

## Alternativas consideradas

- **NestJS** — impõe estrutura e tem ecossistema maduro, mas DI pesada, curva alta e abstração excessiva para time pequeno; nossa estrutura vem de convenção documentada.
- **Fastify** — sólido e rápido, porém preso ao Node e com inferência de tipos inferior; Hono é Web Standards e portátil (edge/serverless para webhooks futuros).
- **Elysia** — melhor inferência, mas na prática Bun-only (lock-in de runtime).
- **tRPC v11** — maior ecossistema, mas OpenAPI só via add-on de terceiros frágil — mataria "documentação automática" e API pública futura.
- **REST puro + @hono/zod-openapi** — alternativa conservadora válida; perde o cliente RPC tipado com helpers TanStack Query que o oRPC dá de graça.
- **Bun como runtime** — ganho real < 3% em workload com I/O de banco; Node LTS vence em previsibilidade.

## Consequências

- (+) Um único lugar (contrato) define input/output; clientes tipados sem geração de código; OpenAPI/docs sempre sincronizados; caminho limpo para API pública.
- (−) oRPC é jovem (v1 dez/2025): versões pinadas via catalog, changelog acompanhado; o contrato OpenAPI é a rota de fuga se precisarmos trocar (clientes migrariam para openapi-fetch).
- (−) Estrutura é responsabilidade nossa — mitigada por spec-driven + revisão.
